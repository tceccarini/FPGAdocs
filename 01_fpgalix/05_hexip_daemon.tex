\chapter{hexip\_daemon}
\label{chap:fpgalix-hexip-daemon}

\section{Introduction}

This chapter builds and deploys the software that lights up the \term{DE1-SoC}'s 7-segment hex displays with the board's \term{IP} address.\footnote{\repopath{sw/hexip_daemon} in the repository.} \cmd{vision_core} (Chapter~\ref{chap:fpgalix-vision-core}) relies on the network connection to stream video, and that address, obtained dynamically over \term{DHCP}, is not known in advance; showing it on the displays makes it available at a glance, without hooking up a serial console every time the board boots just to find the address from the command line before switching over to the network connection.

The program drives the displays through the \hw{hex_display_controller} hardware component (Section~\ref{sec:fpgalix-hex-display}) whose configuration register is reachable through the \gterm{lwhpsbridge}{LW HPS}-to-\gterm{fpga}{FPGA} bridge. The program accesses it directly by mapping that bridge's address range into its own memory with the \ccode{mmap()} function on \extpath{/dev/mem}, a special \term{Linux} device file that exposes the machine's physical address space to user space. The register layout is the one described in Section~\ref{sec:fpgalix-hex-register}.

The \term{IP} address needs to be known as soon as the board finishes booting, so the program is configured to run as a \gterm{daemon}{daemon}: started automatically at boot, and left running unattended in the background afterward. It re-reads the address of a given network interface\footnote{\sysid{eth0} by default, overridable as the first command-line argument.} every three seconds, using the C library function \ccode{getifaddrs()}. Once an \term{IP} address is found, its four octets are displayed in sequence, one second each, separated by a brief blank and followed by a trailing dash, and the cycle repeats. Until an \term{IP} address is found (interface down, no \term{DHCP} lease yet), the display blinks a single dash instead, once a second, so that the daemon's own state remains visible even without an address to show.

\gterm{sigterm}{SIGTERM}\footnote{\glsentrydesc{sigterm}}/\gterm{sigterm}{SIGINT} are handled by turning the display off and releasing the mapping before the process exits.

\section{Driving the display}
\label{sec:fpgalix-hexip-driving}

The daemon reaches \hw{hex_display_controller} (Section~\ref{sec:fpgalix-hex-display}) through its single 32-bit register, mapped at physical address \hw{0xFF200140} on the \gterm{lwhpsbridge}{LW HPS}-to-\gterm{fpga}{FPGA} bridge. Bit 31 enables the display, bits [19:0] carry the value to show, and any value above 999999 forces all six digits to a dash (Section~\ref{sec:fpgalix-hex-register}). The snippet below shows the principle every write to the display rests on, rather than the daemon's logic in full.

\begin{lstlisting}[language=C]
/* register layout: bit 31 = on/off, bits [19:0] = value shown */
#define HEX_DISPLAY_PHYS  0xFF200140UL
#define PAGE_SIZE         0x1000UL
#define PAGE_MASK         (~(PAGE_SIZE - 1))
#define CTRL_ENABLED      (1u << 31)
#define CTRL_DASH         (CTRL_ENABLED | 1000000u)

static volatile uint32_t *hex_reg;

unsigned long page_base   = HEX_DISPLAY_PHYS & PAGE_MASK;
unsigned long page_offset = HEX_DISPLAY_PHYS - page_base;

/* map the register into the process's own address space */
mem_fd   = open("/dev/mem", O_RDWR | O_SYNC);
map_base = mmap(NULL, PAGE_SIZE, PROT_READ | PROT_WRITE,
                MAP_SHARED, mem_fd, page_base);
hex_reg  = (volatile uint32_t *)((char *)map_base + page_offset);

*hex_reg = CTRL_ENABLED | 192;   /* show one octet */
*hex_reg = CTRL_DASH;            /* show "------"  */
*hex_reg = 0;                    /* display off    */
\end{lstlisting}

The register is reached in three steps. \extpath{/dev/mem} exposes the physical address space to a user-space process, and opening it with \ccode{O_SYNC} requests an uncached mapping, so that every write reaches the hardware rather than sitting in a cache line. \ccode{mmap()} can only map whole 4 \term{KiB} memory pages, so it is handed the start of the page containing the register, \hw{0xFF200000}; the register's own offset within that page, \hw{0x140}, is then added back to the address it returns. The resulting pointer is declared \ccode{volatile} to stop the compiler from keeping the location in a register, or from discarding a write merely because the program never reads the value back.

Driving the display is then a single store. \ccode{CTRL_ENABLED} sets bit 31 while the octet, always below 256, occupies the value field unchanged; writing zero blanks all six digits, and \ccode{CTRL_DASH}, deliberately out of the 0--999999 range, produces the all-dash pattern used both as the separator after the fourth octet and as the ``no address yet'' indicator.

\section{Building}
\label{sec:fpgalix-hexip-building}

\begin{shellcodehost}
cd sw/hexip_daemon
export CROSS_COMPILE=arm-none-linux-gnueabihf-
make
\end{shellcodehost}

This produces \repopath{bin/hexip_daemon}.

\section{Deploying as a daemon}
\label{sec:fpgalix-hexip-deploying}

\repopath{sdcard/rootfs_overlay/} already contains what is needed, as two symlinks pointing at this component's own files:

\begin{itemize}
    \item \repopath{opt/FPGAlix/bin/hexip_daemon} $\rightarrow$ \repopath{sw/hexip_daemon/bin/hexip_daemon}, the binary built in Section~\ref{sec:fpgalix-hexip-building}
    \item \repopath{etc/init.d/S60hexip_daemon} $\rightarrow$ \repopath{sw/hexip_daemon/init.d/S60hexip_daemon}, a \gterm{busybox}{BusyBox}-style init script. Placing it under \repopath{etc/init.d/} causes the daemon to be started at boot, while its |S60| prefix sets the startup priority: numbered above the network's own \cmdpath{S40network}, it runs after it, so the network interfaces are already up by the time the daemon starts on \sysid{eth0}.
\end{itemize}

Since these are symlinks, building the daemon is enough for \repopath{rootfs_overlay/} to hold its current binary; no separate install step exists. Deploying it means copying both files onto the \term{SD} card's root filesystem partition (the second partition, \term{ext4}) and rebooting the board:

\begin{shellcodehost}
sudo mount /dev/sdX2 /mnt
sudo mkdir -p /mnt/opt/FPGAlix/bin
sudo cp -L sdcard/rootfs_overlay/opt/FPGAlix/bin/hexip_daemon /mnt/opt/FPGAlix/bin/
sudo cp -L sdcard/rootfs_overlay/etc/init.d/S60hexip_daemon /mnt/etc/init.d/
sudo umount /mnt
\end{shellcodehost}

Replace \extpath{/dev/sdX2} with the \term{SD} card's actual root filesystem partition. On the next boot, the |S60| script starts the daemon automatically.
