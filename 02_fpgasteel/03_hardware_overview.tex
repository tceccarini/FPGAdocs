\chapter{Hardware Overview}
\label{chap:fpgasteel-hw-overview}

\section{Scope of this chapter}
\label{sec:fpgasteel-hw-scope}

\sysname{FPGAsteel} started out as a full copy of the \sysname{FPGAlix} repository, subsequently modified independently. What actually carries over, though, is almost entirely the hardware: the \term{Platform Designer} system this project starts from is \sysname{FPGAlix}'s own |soc_system.qsys|, and everything \sysname{FPGAlix}'s hardware chapter documents about it, namely the rationale for \term{Avalon-ST}/\term{mSGDMA} streaming, the \term{OV7670} sensor and its adapter board, \term{PCLK} generation and its reset problem, the camera acquisition core's state machine, and the rationale for reaching \term{DDR3} through a dedicated \term{SDRAM} port rather than the \term{L3} interconnect, carries over unchanged and is not repeated here. See Hardware Overview (PART~I -- \sysname{FPGAlix}, Chapter~\ref{chap:fpgalix-hw-overview}).

Very little carries over on the software side. Only one boot-chain submodule (|u-boot-socfpga|) is shared between the two repositories. \sysname{FPGAlix}'s own software, under its |sw/| (|camera_driver_2|, |hexip_daemon|, |vision_core|, embedded-\term{Linux} userspace code), has no counterpart here: \sysname{FPGAsteel}'s |sw/| is an unrelated, bare-metal example suite, documented starting from Board Bring-up.\footnote{See Chapter~\ref{chap:fpgasteel-board-bringup}.}

This chapter documents only what changed on top of that starting point: a handful of renamed instances on the camera capture path, a narrower capture datapath with \term{mSGDMA} driven by a hardware descriptor prefetcher instead of software-managed descriptors, and a full \term{VGA} output path with no counterpart in \sysname{FPGAlix}'s hardware (Chapter~\ref{chap:fpgalix-hw-overview}).

The hardware described here is common to every example under |sw/|, currently nine projects. They all target the same |soc_system.qsys| build and the same |FPGAsteel.sof|; what differs between them is the software, not the hardware.

The underlying \term{IP} is unchanged in every case: the first two rows are this project's own custom cores (|ov7670_data_interface|, |pclk_reset_controller|); the remaining three are stock \term{Altera}/\term{Intel} \term{IP} (|altera_avalon_mm_clock_crossing_bridge|, |altera_avalon_dc_fifo|, |altera_avalon_st_adapter|, in the same order).

|ov7670_data_interface| gained a new register, |frame_size|. The hardware behavior is backward compatible with \sysname{FPGAlix}'s version. The |FRAME_SIZE| \term{VHDL} generic still exists, but it no longer fixes the frame size at synthesis time: it now only sets |frame_size|'s value on reset, as a default. From that point on, software can overwrite the register with a different byte count at run time, and the acquisition \term{FSM} uses whatever value the register currently holds. This is what lets the capture path switch between the \term{OV7670}'s 1-byte-per-pixel (\term{RAW}/processed \term{Bayer}) and 2-byte-per-pixel (\term{RGB565}/\term{RGB555}/\term{RGB444}/\term{YUV422}) output formats without recompiling the hardware.

\subsection{mSGDMA configuration}
\label{subsec:fpgasteel-msgdma-config}

Two further changes distinguish the capture path from \sysname{FPGAlix}'s:

\begin{itemize}
    \item \textbf{Width.} \sysname{FPGAlix}'s |st_adapter_0| widens the camera's 8-bit \term{Avalon-ST} stream to 128 bit. This width reflects neither a bandwidth requirement nor the adapter's own maximum capability: with one of the \term{HPS}'s ports already occupied elsewhere, 128 bit was the widest configuration available at the time, adopted because the fabric had sufficient resources to accommodate it.

    \sysname{FPGAsteel}'s |ov7670_st_adapter| widens the same stream to 64 bit only, because adding the \term{VGA} output path to the same fabric leaves less room to spend on this width.

    The capture path itself would have worked with less than 64 bit, even 8 bit would have carried the required throughput, but going narrower would not have saved any resource: the dedicated \term{FPGA}-to-\term{HPS} \term{SDRAM} port each \term{mSGDMA} uses is provisioned the same way for any \term{Avalon-MM} interface up to 64 bit.\footnote{A 32- or 64-bit \term{Avalon-MM} interface, read-only or write-only, costs exactly one command port and one data port; only at 128 bit does the port cost double \cite[Table 12-3, p.~12-6]{CV-TRM}. The underlying data ports are natively 64-bit regardless of the configured interface width, so no narrower configuration costs less \cite[Table 12-2, p.~12-5]{CV-TRM}.} With the same 512-beat maximum burst count on the \term{mSGDMA} that follows it (|MAX_BURST_COUNT| is 512 in both projects), the largest single burst into \term{DDR3} drops from 8 \term{KiB} (\sysname{FPGAlix}) to 4 \term{KiB} (\sysname{FPGAsteel}).
    \item \textbf{Descriptor management.} \sysname{FPGAsteel} enables the \term{mSGDMA}'s hardware descriptor prefetcher, where \sysname{FPGAlix} left it disabled and managed descriptors from software instead. The platform each project runs on drives this difference: \sysname{FPGAlix} runs embedded \term{Linux}, where using the prefetcher would have required developing a dedicated kernel driver for it. \sysname{FPGAsteel} is bare-metal, with direct access to the hardware, so enabling the prefetcher doesn't cost a \term{Linux} kernel integration, only a few register writes.

    |ov7670_video_msgdma| fetches successive descriptors on its own out of a dedicated on-chip \term{RAM}, |ov7670_prefercher_descriptor_mem|, re-arming itself between frames without \term{CPU} intervention.

    \sysname{FPGAlix}'s |sc_fifo_0|, a buffer \term{FIFO} placed there to mitigate frame loss when memory and \term{CPU} were under load, has no counterpart here. This is not simply because descriptors now live on-chip rather than in \term{DDR3}; it is because the whole re-arm path is faster and more deterministic than in \sysname{FPGAlix}: bare-metal software re-arms each descriptor from its interrupt handler with lower, more predictable latency than a \term{Linux} driver would, and the on-chip descriptor memory itself is read directly, at \term{SRAM} speed, without \term{DDR3}'s burst-oriented access and \term{MPFE} arbitration overhead. Together, these remove the latency |sc_fifo_0| existed to absorb. How the prefetcher itself operates (descriptor layout, ping-pong buffering) is documented in full in Paragraph~\ref{subsec:fpgasteel-descriptors-prefetcher} and is not repeated here.
\end{itemize}

\section{VGA output path (new)}
\label{sec:fpgasteel-vga-output}

\sysname{FPGAsteel} adds a second, symmetric datapath in the \term{FPGA} fabric, \term{Avalon-MM}$\rightarrow$\term{ST} this time, that reads frames back out of \term{DDR3} and drives the \term{DE1-SoC}'s \term{VGA} connector directly, mirroring the capture path in reverse (software side: Paragraph~\ref{subsec:fpgasteel-simple-forwarding-vga-output}). None of the components below exist in \sysname{FPGAlix} \term{Platform Designer}'s system:

\begin{itemize}
    \item \textbf{\texttt{vga\_pll}} (|altera_pll|): generates a fixed 25 \term{MHz} pixel clock from |clk_0| (the board's 50 \term{MHz} oscillator, the same |sys_clk| source everything else in the design uses).
    \item \textbf{\texttt{vga\_reset\_syncronizer}} (kind |pll_lock_reset_sync|, a new custom component, source |hw/my_vhdl/qsys_components/pll_lock_reset_sync.vhd|, distinct from |pclk_reset_controller|): releases the reset for the |vga_clk| domain only once the system reset is released and |vga_pll| reports locked.
    \item \textbf{\texttt{vga\_msgdma}} (|altera_msgdma|, \term{MM}$\rightarrow$\term{ST} direction): the read-back counterpart of |ov7670_video_msgdma|, equally prefetcher-enabled with its own on-chip descriptor \term{RAM}, |vga_prefercher_descriptor_mem|.
    \item \textbf{\texttt{vga\_dc\_fifo}} crosses the stream from |sys_clk| into the |vga_clk| domain immediately after |vga_msgdma.st_source|, while the stream is still kept at 64 bit wide.
    \item \textbf{\texttt{vga\_64\_to\_24\_repacker}} (kind |avalon_st_64_to_24_repacker|, new custom \term{IP}, source |hw/my_vhdl/qsys_components/avalon_st_64_to_24_repacker.vhd|): named for the color depth it carries, \term{RGB888}, not for its output wire width. |vga_controller|'s \term{Avalon-ST} sink is fixed by the University Program \term{IP} at 30 bit (|dataBitsPerSymbol|=10, |symbolsPerBeat|=3, \term{RGB101010}), and \term{Platform Designer}'s automatic width adapter cannot bridge an 8-bit-symbol stream to a 10-bit-symbol one, since the symbol width itself changes and not just the beat count. This component narrows the stream from 64 bit down to 24 bit, then zero-extends each 8-bit \term{RGB888} channel into its own 10-bit slot (2 zero low-order bits per channel), producing exactly the 30-bit \term{RGB101010} beat |vga_controller| expects, one pixel per beat, entirely inside the |vga_clk| domain, after the crossing above.
    \item \textbf{\texttt{vga\_controller}} (|altera_up_avalon_video_vga_controller|, standard Altera University Program \term{IP}): drives the \term{DE1-SoC}'s \term{VGA} connector's sync and color signals at a fixed $640\times480$.
    \item A third dedicated \textbf{\term{FPGA}-to-\term{HPS} \term{SDRAM} port.} \sysname{FPGAlix} uses two: |f2h_sdram0_data|, wired to a \term{JTAG} \term{Avalon} master (|f2sdram_only_master|, kind |altera_jtag_avalon_master|) for debug access, and |f2h_sdram1_data| for its \term{mSGDMA}. \sysname{FPGAsteel} simply adds a third, |f2h_sdram2_data|, for |vga_msgdma|, for the same reason \sysname{FPGAlix} gives its own \term{mSGDMA} a dedicated port instead of routing through the \term{L3} interconnect (PART~I -- \sysname{FPGAlix}, Paragraph~\ref{sec:fpgalix-sdram-port}).
\end{itemize}
