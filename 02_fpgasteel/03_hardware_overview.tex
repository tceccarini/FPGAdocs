\chapter{Hardware Overview}
\label{chap:fpgasteel-hw-overview}

\section{Scope of this chapter}
\label{sec:fpgasteel-hw-scope}

\prjname{FPGAsteel} started out as a full copy of the \prjname{FPGAlix} repository, subsequently modified independently. What actually carries over, though, is almost entirely the hardware: the \gterm{platformdesigner}{Platform Designer} system this project starts from is \prjname{FPGAlix}'s own \repopath{soc_system.qsys}. Everything \prjname{FPGAlix}'s hardware chapter documents about it carries over unchanged and is not repeated here: the rationale for \gterm{avalonst}{Avalon-ST}\footnote{\glsentrydesc{avalonst}}/\gterm{msgdma}{mSGDMA}\footnote{\glsentrydesc{msgdma}} streaming, the \gterm{ov7670}{OV7670} sensor and its adapter board, \gterm{pclk}{PCLK}\footnote{\glsentrydesc{pclk}} generation and its reset problem, the camera acquisition core's state machine, and the rationale for reaching \term{DDR3} through a dedicated \term{SDRAM} port rather than the \term{L3} interconnect. See Hardware Overview (PART~I -- \prjname{FPGAlix}, Chapter~\ref{chap:fpgalix-hw-overview}).

Very little carries over on the software side. Only one boot-chain submodule (|u-boot-socfpga|) is shared between the two repositories. \prjname{FPGAlix}'s own software, under its \repopath{sw/} folder (\cmd{camera_driver_2}, \cmd{hexip_daemon}, \cmd{vision_core}, embedded-\term{Linux} userspace code), has no counterpart here: \prjname{FPGAsteel}'s \repopath{sw/} folder is an unrelated, bare-metal example suite, documented starting from \nameref{chap:fpgasteel-board-bringup}.

The following sections document only what changed on top of that starting point: a handful of renamed instances on the camera capture path, a narrower capture datapath with \gterm{msgdma}{mSGDMA} driven by a hardware descriptor prefetcher instead of software-managed descriptors, and a full \gterm{vga}{VGA} output path with no counterpart in \prjname{FPGAlix}'s hardware (Chapter~\ref{chap:fpgalix-hw-overview}).

The hardware described here is common to every example under \repopath{sw/}: none of them requires recompiling it, regenerating its bitstream, or rebuilding the bootloader; only the software differs between them.

All these instances remain the same type, except for the custom \term{IP} \hw{ov7670_data_interface}, for which a hardware update was made. Here, the frame size is no longer bound to the value of the \ccode{FRAME_SIZE} \gterm{vhdl}{VHDL} generic set during hardware compilation, but can now be changed by writing the \ccode{frame_size} register, accessible over the \gterm{avalonmm}{Avalon-MM}\footnote{\glsentrydesc{avalonmm}} bus. To preserve backward compatibility, the \ccode{FRAME_SIZE} generic remains settable, but it now only determines the value loaded into the \ccode{frame_size} register at reset. This is what lets the capture path switch between the \gterm{ov7670}{OV7670}'s 1-byte-per-pixel (\term{RAW}/processed \term{Bayer}) and 2-byte-per-pixel (\gterm{rgb565}{RGB565}\footnote{\glsentrydesc{rgb565}}/\gterm{rgb555}{RGB555}\footnote{\glsentrydesc{rgb555}}/\gterm{rgb444}{RGB444}\footnote{\glsentrydesc{rgb444}}/\gterm{yuv422}{YUV422}\footnote{\glsentrydesc{yuv422}}) output formats without recompiling the hardware.

\subsection{mSGDMA configuration}
\label{subsec:fpgasteel-msgdma-config}

\subsubsection{Descriptor prefetching}

Beyond the dispatcher and the Read/Write Host pair covered in PART~I -- \prjname{FPGAlix}, Paragraph~\ref{subsec:fpgalix-msgdma}, the \gterm{msgdma}{mSGDMA} \term{IP} offers one further optional module: the \emph{prefetcher}, which attaches directly to the dispatcher's descriptor input (Figure~\ref{fig:fpgasteel-msgdma-prefetcher}). Rather than software writing one descriptor at a time, the prefetcher fetches successive descriptors directly from memory on its own, following the chain each descriptor's next-pointer field defines, and writes the completion status back to the same location once each transfer finishes.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\linewidth]{MsgdmaPrefetcherStToMmIntelManual}
    \caption{mSGDMA module configuration with a prefetcher and a Write Host attached, supporting \term{Avalon-ST} to \term{Avalon-MM} transfers (source: \cite[Figure 109, p.~378]{EP-IPUG}).}
    \label{fig:fpgasteel-msgdma-prefetcher}
\end{figure}

\prjname{FPGAsteel} enables this module; \prjname{FPGAlix} does not, since doing so under embedded \term{Linux} would have required developing a dedicated kernel driver for it, whereas here, running bare-metal with direct access to the hardware, enabling it costs only direct register writes.

\subsubsection{Descriptor memory}

Wiring its descriptor master ports is itself a further choice: one option is to reach system \term{DDR3} through the general-purpose \gterm{fpga}{FPGA}-to-\gterm{hps}{HPS} bridge, crossing the \gterm{hps}{HPS}'s \term{L3} interconnect (the yellow path in PART~I -- \prjname{FPGAlix}, Figure~\ref{fig:fpgalix-hps-block-diagram}). \prjname{FPGAlix} suffered frame-loss problems under load; rather than reaching \term{DDR3} the same way here, \prjname{FPGAsteel} tries a different approach, dedicating a small on-chip \term{RAM} (\hw{ov7670_prefercher_descriptor_mem}) to this purpose instead, one per \gterm{msgdma}{mSGDMA} instance: memory with no other master to contend with, favouring low, deterministic latency over the burst-oriented access \term{DDR3} would require. This \term{RAM} is dual-port: one port faces the fabric, wired directly to the prefetcher; the other faces the \gterm{hps}{HPS}, reached over the \gterm{hps}{HPS}-to-\gterm{fpga}{FPGA} bridge instead, so that software can still set up and inspect descriptors from outside the fabric.

\prjname{FPGAlix}'s \hw{sc_fifo_0}, a buffer \term{FIFO} placed there to mitigate frame loss when memory and \term{CPU} were under load, has no counterpart here: the deterministic, low-latency re-arm path described above removes the latency it existed to absorb. How the prefetcher itself operates (descriptor layout, ping-pong buffering) is documented in full in Paragraph~\ref{subsec:fpgasteel-descriptors-prefetcher} and is not repeated here.

\subsubsection{Stream width}

\prjname{FPGAlix}'s \hw{st_adapter_0} widens the camera's 8-bit \gterm{avalonst}{Avalon-ST} stream to 128 bit. This width reflects neither a bandwidth requirement nor the adapter's own maximum capability: with one of the \gterm{hps}{HPS}'s DRAM controller ports already occupied, 128 bit was the widest configuration available at the time, adopted because the fabric had sufficient resources to accommodate it.

\prjname{FPGAsteel}'s \hw{ov7670_st_adapter} widens the same stream to 64 bit only, because adding the \gterm{vga}{VGA} output path to the same fabric leaves less room to spend on this width.

The capture path itself would have worked with less than 64 bit, even 8 bit would have carried the required throughput, but going narrower would not have saved any resource: the dedicated \gterm{fpga}{FPGA}-to-\gterm{hps}{HPS} \term{SDRAM} port each \gterm{msgdma}{mSGDMA} uses is provisioned the same way for any \gterm{avalonmm}{Avalon-MM} interface up to 64 bit.\footnote{A 32- or 64-bit \gterm{avalonmm}{Avalon-MM} interface, read-only or write-only, costs exactly one command port and one data port; only at 128 bit does the port cost double \cite[Table 12-3, p.~12-6]{CV-TRM}. The underlying data ports are natively 64-bit regardless of the configured interface width, so no narrower configuration costs less \cite[Table 12-2, p.~12-5]{CV-TRM}.} The \gterm{msgdma}{mSGDMA} \term{IP}'s 512-beat maximum burst count itself is unchanged; since the largest single burst into \term{DDR3} follows directly from it, it drops from 8 \term{KiB} at 128 bit (\prjname{FPGAlix}) to 4 \term{KiB} at 64 bit (\prjname{FPGAsteel}).

\section{VGA output path (new)}
\label{sec:fpgasteel-vga-output}

\prjname{FPGAsteel} adds a second, symmetric datapath in the \gterm{fpga}{FPGA} fabric, \gterm{avalonmm}{Avalon-MM}$\rightarrow$\term{ST} this time, that reads frames back out of \term{DDR3} and drives the \term{DE1-SoC}'s \gterm{vga}{VGA} port directly, mirroring the capture path in reverse (software side: Paragraph~\ref{subsec:fpgasteel-simple-forwarding-vga-output}). None of the components below exist in \prjname{FPGAlix} \gterm{platformdesigner}{Platform Designer}'s system:

\begin{itemize}
    \item \textbf{\hw{vga_pll}} (kind |altera_pll|): generates a fixed 25 \term{MHz} pixel clock from \hw{clk_0} (the board's 50 \term{MHz} oscillator, the same \hw{sys_clk} source everything else in the design uses).
    \item \textbf{\hw{vga_reset_syncronizer}} (kind |pll_lock_reset_sync|, a new custom component, source \repopath{hw/my_vhdl/qsys_components/pll_lock_reset_sync.vhd}): releases the reset for the \hw{vga_clk} domain only once the system reset is released and \hw{vga_pll} reports locked.
    \item \textbf{\hw{vga_msgdma}} (kind |altera_msgdma|, \term{MM}$\rightarrow$\term{ST} direction): the read-back counterpart of \hw{ov7670_video_msgdma}, equally prefetcher-enabled with its own on-chip descriptor \term{RAM}, \hw{vga_prefercher_descriptor_mem}.
    \item \textbf{\hw{vga_dc_fifo}} (kind |altera_avalon_dc_fifo|): crosses the stream from \hw{sys_clk} into the \hw{vga_clk} domain immediately after \hw{vga_msgdma}'s \gterm{avalonst}{Avalon-ST} source port, while the stream is still kept at 64 bit wide.
    \item \textbf{\hw{vga_64_to_24_repacker}} (kind |avalon_st_64_to_24_repacker|, new custom \term{IP}, source \repopath{hw/my_vhdl/qsys_components/avalon_st_64_to_24_repacker.vhd}): named for the color depth it carries, \term{RGB888}, not for its output wire width. \hw{vga_controller}'s \gterm{avalonst}{Avalon-ST} sink is fixed by the Intel University Program \term{IP} at 30 bit (\ccode{dataBitsPerSymbol}=10, \ccode{symbolsPerBeat}=3, \term{RGB101010}), and \gterm{platformdesigner}{Platform Designer}'s automatic width adapter cannot bridge an 8-bit-symbol stream to a 10-bit-symbol one, since the symbol width itself changes and not just the beat count. This component narrows the stream from 64 bit down to 24 bit, then zero-extends each 8-bit \term{RGB888} channel into its own 10-bit slot (2 zero low-order bits per channel), producing exactly the 30-bit \term{RGB101010} beat \hw{vga_controller} expects, one pixel per beat, entirely inside the \hw{vga_clk} domain, after the crossing above.
    \item \textbf{\hw{vga_controller}} (kind |altera_up_avalon_video_vga_controller|, standard Altera University Program \term{IP}): drives the \term{DE1-SoC}'s \gterm{vga}{VGA} connector's sync and color signals at a fixed $640\times480$.
    \item A third dedicated \textbf{\gterm{fpga}{FPGA}-to-\gterm{hps}{HPS} \term{SDRAM} port.} \prjname{FPGAlix} uses two: \hw{f2h_sdram0_data}, wired to a \gterm{jtag}{JTAG} \term{Avalon} master for debug access, and \hw{f2h_sdram1_data} for its camera-capture \gterm{msgdma}{mSGDMA}. \prjname{FPGAsteel} simply adds a third, \hw{f2h_sdram2_data} port, for \hw{vga_msgdma}, for the same reason \prjname{FPGAlix} gives its own \gterm{msgdma}{mSGDMA} a dedicated port instead of routing through the \term{L3} interconnect (PART~I -- \prjname{FPGAlix}, Paragraph~\ref{sec:fpgalix-sdram-port}).
\end{itemize}

Compared to \prjname{FPGAlix}, block memory usage drops from 70\% to 55\%: \hw{sc_fifo_0} has no counterpart here, since the hardware prefetcher's on-chip descriptor memory re-arms each transfer deterministically enough that the frame-loss mitigation it existed for is not needed (Paragraph~\ref{subsec:fpgasteel-msgdma-config}). Logic usage goes the other way, from 15\% to 18\% \term{ALM}s and from 7{,}434 to 9{,}103 registers: the extra components are the descriptor prefetcher itself (Paragraph~\ref{subsec:fpgasteel-msgdma-config}), enabled on both \gterm{msgdma}{mSGDMA} cores here against \prjname{FPGAlix}'s single, software-managed one, and the whole \gterm{vga}{VGA} output datapath (Section~\ref{sec:fpgasteel-vga-output}), which has no counterpart there at all. The \term{I/O} pin count rises correspondingly, from 51\% to 57\%, and this is also the only one of the two projects using a \term{PLL}, for the \gterm{vga}{VGA} clock.
