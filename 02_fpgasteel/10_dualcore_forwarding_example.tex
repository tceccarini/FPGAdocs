\section{About this project}
\label{sec:fpgasteel-dualcore-forwarding-about}

\textit{``Dual-Core Forwarding Example''} (under \repopath{sw/dualcore_forwarding_example}) combines the two previous projects: the camera-to-\gterm{vga}{VGA} pipeline with cache management from \nameref{chap:fpgasteel-cache-forwarding}, and the \term{CPU1} bring-up mechanism from \nameref{chap:fpgasteel-dualcore-bringup}. What is new here is the reason to bring \term{CPU1} up at all: instead of just proving \term{CPU1} can run independently, this project actually hands it work, splitting the \gterm{rgb565}{RGB565}-to-\term{RGB24} conversion of every captured frame in half, one half per core, through a small dispatch mechanism built on top of the bring-up sequence from \nameref{chap:fpgasteel-dualcore-bringup}.

At startup, in addition to what \nameref{chap:fpgasteel-cache-forwarding} already does, this project:

\begin{itemize}
 \item brings up the shared \gterm{mmu}{MMU} page table, the \gterm{scu}{SCU}, and the \term{L2} cache once, from \term{CPU0} (\ccode{System::prepareCacheSubsystem()}), then enables the \gterm{mmu}{MMU} and \term{L1} data cache on each core individually (\ccode{System::initCore()}, Paragraph~\ref{subsec:fpgasteel-dualcore-forwarding-shared-mmu}); unlike Cache Forwarding Example, \ccode{initCore()} can also enable the \term{L1} instruction cache on each core, controlled by a single compile-time flag;
 \item boots \term{CPU1} (\ccode{Core1::start()}, Paragraph~\ref{subsec:fpgasteel-dualcore-forwarding-bringing-cpu1}), using the same reset/trampoline/cache-clean/release sequence as Dual-Core Bring-up Test, and waits for it to report itself ready before doing anything else.
\end{itemize}

Everything else, the descriptor/prefetcher mechanism, the camera and \gterm{vga}{VGA} ISRs, \ccode{CacheAwareFrame}/\ccode{CacheAwareFramePool}, is unchanged from \nameref{chap:fpgasteel-cache-forwarding}; Section~\ref{sec:fpgasteel-dualcore-forwarding-code-structure} covers each class by reference, only writing new text where something actually differs.

\section{Prerequisites}
\label{sec:fpgasteel-dualcore-forwarding-prerequisites}

Same toolchain, \term{SD card} and \term{Eclipse}/\gterm{openocd}{OpenOCD} debug setup as \nameref{chap:fpgasteel-hello-world}, plus the \gterm{ov7670}{OV7670} camera adapter board on \term{GPIO\_0} as described in \nameref{chap:fpgasteel-i2c-example} (Section~\ref{sec:fpgasteel-i2c-prerequisites}). The boot script is the same \repopath{boot.script.jtag_debug} used by every other example; this project brings its own caches and \gterm{mmu}{MMU} up entirely through \ccode{System::prepareCacheSubsystem()}/\ccode{initCore()}, which does not depend on whatever cache state the boot script left behind.

\begin{warningbox}
\textbf{Hardware bug:} do not leave the camera in \term{RESET} or \term{POWER-DOWN} for extended periods.\footnotemark
\end{warningbox}
\footnotetext{See Part~\ref{part:appendices}, Section~\ref{sec:camera-adapter-reset-powerdown}.}

Two additional requirements, inherited from \nameref{chap:fpgasteel-dualcore-bringup} (Section~\ref{sec:fpgasteel-dualcore-prerequisites}), and equally necessary here since \term{CPU1} is brought up the same way:

\begin{itemize}
 \item \gterm{openocd}{OpenOCD} must only ever attach to \term{CPU0} (\ccode{CHIPCORES=1}, not 2).
 \item ``Initial Reset'' and ``Pre-run/Restart reset'' must both be disabled in the debug configuration, and ``Enable Arm semihosting'' must be enabled, for the same reason as Dual-Core Bring-up Test: a reset reissued by \gterm{openocd}{OpenOCD} mid-session would reassert \term{CPU1}'s reset line again, undoing the bring-up.
\end{itemize}

\section{Operating principles}
\label{sec:fpgasteel-dualcore-forwarding-operating-principles}

\subsection{Bringing CPU1 up}
\label{subsec:fpgasteel-dualcore-forwarding-bringing-cpu1}

Bringing \term{CPU1} up uses the exact same mechanism as \nameref{chap:fpgasteel-dualcore-bringup} (Section~\ref{sec:fpgasteel-dualcore-operating-principles}), just packaged differently: everything specific to \term{CPU1} now lives in one \gterm{singleton}{singleton} class called \ccode{Core1}, whose methods both start the core and manage the work later handed to it. At hardware reset \term{CPU1} stays held in reset, which is why \ccode{Core1}'s status defaults to \ccode{Offline}. Calling \ccode{Core1::start()} moves it to \ccode{Starting} status and runs the already-shown release sequence, finishing with \term{CPU1} landing in \ccode{Core1::run()}, which is the main loop that will later accept dispatched work. Once \ccode{run()} finishes its own setup, \ccode{Core1} moves to \ccode{Ready}.

\subsection{The Worker/DualCoreJob dispatch mechanism}
\label{subsec:fpgasteel-dualcore-forwarding-dispatch}

This project's scheduler is built to manage jobs that need both cores. It rests on two abstract (i.e., interface) classes, \ccode{DualCoreJob} and \ccode{Worker}. Any task that needs to use both cores must override \ccode{DualCoreJob}'s interface methods: \ccode{start()}, which launches the job on both cores; \ccode{getWorker0()} and \ccode{getWorker1()}, which return the workers that will be assigned to each \term{CPU}; \ccode{awaitDone()}, which blocks the calling flow until both workers have finished; and \ccode{isErrorOccured()}/\ccode{whatError()}, which let the caller check whether an error occurred during the computation. The abstract class \ccode{Worker} exposes the \ccode{run()} method, executed by whichever core it is assigned to, and a \ccode{status} field that defaults to \ccode{Stopped}.

As a concrete example, \ccode{DualCoreFormatConverter} implements \ccode{DualCoreJob} to split one frame's pixel-format conversion across the two cores, as shown in Figure~\ref{fig:fpgasteel-dualcore-forwarding-dispatch-sequence}: \term{CPU0} converts the top half, \term{CPU1} the bottom half. The workers are instances of the class \ccode{HalfFrameWorker}: each one contains the format-conversion code itself, plus a few fields that set what to operate on -- the source/destination pointers, the frame's width and height, and the source color scheme. These instances are exactly what \ccode{getWorker0()} and \ccode{getWorker1()} return. \ccode{DualCoreFormatConverter::start()} dispatches the bottom-half worker (\ccode{m_worker1}) to \term{CPU1} through the \ccode{Core1::dispatch()} method, which first waits for any previous job to finish, then hands the worker off, setting its status to \ccode{Ready} and storing its pointer in \ccode{Core1}'s own worker slot. Inside \ccode{Core1::run()}, the polling loop notices the newly assigned worker, switches its status to \ccode{Running}, and calls the worker's own \ccode{run()} method -- the bottom half's conversion, in this case. Meanwhile, \term{CPU0} runs the top-half worker sequentially, right there inside \ccode{start()} itself. At this point, the main execution flow, running on \term{CPU0}, calls \ccode{awaitDone()}, which simply polls the bottom-half worker's status until it reaches \ccode{Completed} or \ccode{Error}, set by \ccode{Core1::run()}. \ccode{isErrorOccured()} and \ccode{whatError()} can now check each worker's own status and error message. \ccode{HalfFrameWorker::run()} is where the real work happens: it converts its half of the frame to \term{RGB24} and, since it may run on either core, ends by cleaning its own \term{L1} cache lines for the half it just wrote, so the result is visible to whichever core reads it next.

 \includesvg[width=\linewidth]{FPGAsteelWorkerDispatchSequence}

 \label{fig:fpgasteel-dualcore-forwarding-dispatch-sequence}
\end{figure}

This whole scheme stays safe without a mutex or semaphore because exactly one core ever writes to each shared field: only \term{CPU0} calls \ccode{Core1::dispatch()}, and only \term{CPU1}, inside \ccode{Core1::run()}, ever clears \ccode{Core1}'s worker slot back to \ccode{nullptr}. With a single writer per field, and \ccode{dispatch()}'s own wait ensuring only one job is ever in flight at a time, plain atomic reads and writes are all the synchronization this needs -- the same reasoning that already lets \ccode{FramePool} work lock-free.

\subsection{Shared MMU, per-core caches}
\label{subsec:fpgasteel-dualcore-forwarding-shared-mmu}

The \gterm{scu}{SCU}/\term{L1}/\term{L2} architecture is the one in Figure~\ref{fig:fpgasteel-cortex-a9-mpu-subsystem} on page~\pageref{fig:fpgasteel-cortex-a9-mpu-subsystem}, already reproduced in \nameref{chap:fpgasteel-cache-forwarding}. Unlike Cache Forwarding Example, where only one core ever runs, this project has two cores that both need cache and \gterm{mmu}{MMU} support, and a page table is not something that can safely be built twice. The work is split into two methods on \ccode{System}:

\begin{itemize}
 \item \ccode{prepareCacheSubsystem()}, called once, from \term{CPU0}, before \term{CPU1} starts: enables the \gterm{scu}{SCU}, disables whatever cache state \gterm{uboot}{U-Boot} left behind, declares the same three-region flat 1:1 mapping as Cache Forwarding Example's \ccode{System::enableCache()} and hands it, together with a storage allocator, to \ccode{alt_mmu_va_space_create()}; \gterm{hwlib}{hwlib} is what actually writes the section table into that storage, exactly as in Subparagraph~\ref{subsubsec:fpgasteel-hwlib-performs-work}. \ccode{prepareCacheSubsystem()} then enables the \term{L2} cache and calls \ccode{initCore()} for \term{CPU0} itself.
 \item \ccode{initCore()}, called once per core (by \ccode{prepareCacheSubsystem()} for \term{CPU0}, and again by \ccode{Core1::run()} for \term{CPU1} after it starts): enables the \gterm{vfp}{VFP}\footnote{\glsentrydesc{vfp}}/\gterm{neon}{NEON} coprocessor access bits (\term{CPU1} does not inherit this from \gterm{uboot}{U-Boot} the way \term{CPU0} does), sets the \hw{ACTLR.SMP} bit to join the \gterm{scu}{SCU} coherency domain, points the \gterm{mmu}{MMU} at the one shared table via \ccode{alt_mmu_va_space_enable()}, and enables the \term{L1} data cache. It also optionally enables the \term{L1} instruction cache on each core, gated behind the \ccode{ICACHE_ENABLE} compile-time flag (\repopath{Config.h}); Cache Forwarding Example has no equivalent switch at all, since it never touches the instruction cache.
\end{itemize}

Both cores' \gterm{mmu}{MMU}s are pointed, via \ccode{alt_mmu_va_space_enable()}, at the exact same translation table (\ccode{s_ttb1}, built once by \gterm{hwlib}{hwlib} inside \ccode{prepareCacheSubsystem()}): each core has its own private \gterm{tlb}{TLB}\footnote{\glsentrydesc{tlb}} caching entries from it, but the entries themselves, and therefore the memory attributes every address gets, are identical on both cores. This matters for Paragraph~\ref{subsec:fpgasteel-dualcore-forwarding-cache-coherency}: if the two cores disagreed on which regions were cacheable, keeping them coherent with each other would not even be well-defined.

\subsection{Cache coherency across two cores, and into DMA}
\label{subsec:fpgasteel-dualcore-forwarding-cache-coherency}

\ccode{DualCoreFormatConverter} splits one frame conversion into a top half, run synchronously on \term{CPU0}, and a bottom half, dispatched to \term{CPU1} through the mechanism above. Paragraph~\ref{subsec:fpgasteel-dualcore-forwarding-shared-mmu} already put both cores in the same \gterm{scu}{SCU} coherency domain, which means a plain memory write by one core is automatically visible to a subsequent read by the other, no cache instruction required, which is exactly what lets \term{CPU0} poll \ccode{m_worker1.status} and see \term{CPU1}'s updates to it at all.

That automatic coherency covers the two \term{ARM} cores only. It says nothing about the two \gterm{msgdma}{mSGDMA} cores in the \gterm{fpga}{FPGA} fabric: as established in Subparagraph~\ref{subsubsec:fpgasteel-dma-cache-coherency}, those \gterm{dma}{DMA} masters read and write \term{DDR} directly and are not part of the \gterm{scu}{SCU}'s coherency domain, exactly as on Cache Forwarding Example. So, the converted frame still needs the same clean-before-\gterm{dma}{DMA}-reads treatment Cache Forwarding Example established; the only question is which core is responsible for it.

A cache clean instruction only ever operates on the core that executes it: a clean issued on \term{CPU0} cannot reach into \term{CPU1}'s own \term{L1} cache banks and force them to write back, and vice versa. This is why \ccode{DualCoreFormatConverter::HalfFrameWorker::run()} (\repopath{DualCoreFormatConverter.cpp}) ends with its own cache clean\footnote{Through the \gterm{hwlib}{hwlib} function \ccode{alt_cache_l1_data_clean(dst, width * height * 3)}.} on the half it just wrote, executed by whichever core actually ran that particular worker: \term{CPU0} cleans its own half's \term{L1} lines synchronously, right after converting it; \term{CPU1} cleans its own half's \term{L1} lines from inside \ccode{Core1::run()}'s worker loop, right after its own \ccode{run()} returns. Each core can only clean what it itself dirtied, so each core does exactly that, immediately.

That still only gets both halves as far as the shared \term{L2}, not to \term{DDR}. The final step is the same one Cache Forwarding Example already relies on: \ccode{vgaPool.push(vgaFrame, true)} (\repopath{main0.cpp}, Section~\ref{sec:fpgasteel-dualcore-forwarding-how-it-works}) calls \ccode{CacheAwareFrame::cacheFlush()}, which cleans both \term{L1} and \term{L2} for the whole buffer, but only from \term{CPU0}, the core that calls it. By that point \term{CPU0}'s own half is already clean (the per-worker clean above made that a harmless no-op), and \term{CPU1}'s half, already pushed out of \term{CPU1}'s \term{L1} into the shared \term{L2} by its own per-worker clean, is exactly what this last, single \term{L2} clean reaches and finally pushes on to \term{DDR}. Two per-core \term{L1} cleans, one shared \term{L2}-and-\term{DDR} clean: that is the whole coherency story for a frame two cores wrote together.

\subsection{Worker class}
\label{subsec:fpgasteel-dualcore-forwarding-worker}

Abstract base for one unit of work executed on a single core, and the foundation of the dispatch mechanism in Paragraph~\ref{subsec:fpgasteel-dualcore-forwarding-dispatch}. Source: \repopath{Worker.h}.

\begin{itemize}
 \item \ccode{status} (public \ccode{std::atomic<Status>} member, not a method): the cross-core lifecycle flag itself (\ccode{Stopped} $\rightarrow$ \ccode{Ready} $\rightarrow$ \ccode{Running} $\rightarrow$ \ccode{Completed} $\mid$ \ccode{Error}), written by whichever core executes the worker, read by whichever core submitted it.
 \item \ccode{run()} (pure virtual, \ccode{noexcept}): the actual payload. Must not throw; must set \ccode{status} to \ccode{Error} itself on failure instead.
 \item \ccode{whatError()} (pure virtual): human-readable description of the last error, valid when \ccode{status} is \ccode{Error}.
\end{itemize}

\subsection{DualCoreJob class}
\label{subsec:fpgasteel-dualcore-forwarding-dualcore-job}

Abstract coordinator interface for a piece of work split into exactly two \ccode{Worker}s, one per core; \ccode{DualCoreFormatConverter} is its only implementation in this project. Source: \repopath{DualCoreJob.h}.

\begin{itemize}
 \item \ccode{start()} (pure virtual): launches both workers.
 \item \ccode{awaitDone()} (pure virtual): blocks until both have reached \ccode{Completed} or \ccode{Error}.
 \item \ccode{getWorker0()}/\ccode{getWorker1()} (pure virtual): access to the two underlying \ccode{Worker}s.
 \item \ccode{isErrorOccured()} (pure virtual): true if either worker ended in \ccode{Error}.
 \item \ccode{whatError(cpuNum)} (pure virtual): error description for the given core (0 or 1).
\end{itemize}

\subsection{Core1 class}
\label{subsec:fpgasteel-dualcore-forwarding-core1}

\gterm{singleton}{Singleton} owning everything about \term{CPU1}: bringing it up and dispatching work to it. Source: \lstinline[style=inlineFsRepo]!Core1.{h,cpp}!.

\begin{itemize}
 \item \ccode{getInstance()}: returns the \gterm{singleton}{singleton} instance.
 \item \ccode{start()}: runs the bring-up sequence from Paragraph~\ref{subsec:fpgasteel-dualcore-forwarding-bringing-cpu1}. Must be called once, from \term{CPU0}, after \ccode{System::prepareCacheSubsystem()}.
 \item \ccode{getStatus()}: returns \ccode{Offline}/\ccode{Starting}/\ccode{Ready}/\ccode{Error}; \term{CPU0} polls this after \ccode{start()} to know when \term{CPU1} has finished its own \ccode{initCore()} and is ready to accept work.
 \item \ccode{whatError()}: error description, valid when \ccode{getStatus()} is \ccode{Error}.
 \item \ccode{dispatch(worker)}: hands \ccode{worker} to \term{CPU1}, as described in Paragraph~\ref{subsec:fpgasteel-dualcore-forwarding-dispatch}. Blocks until \term{CPU1}'s slot is free.
 \item \ccode{isIdle()}: true if no worker is currently assigned to \term{CPU1}.
 \item \ccode{run()} (private, \ccode{noexcept}, called only from \ccode{main1()} on \term{CPU1}): calls \ccode{System::initCore()} for \term{CPU1}, marks \ccode{status} \ccode{Ready}, then loops forever picking up and running whatever \ccode{dispatch()} places in the slot.
\end{itemize}

\subsection{DualCoreFormatConverter class}
\label{subsec:fpgasteel-dualcore-forwarding-dualcore-format-converter}

Implements \ccode{DualCoreJob} and extends \ccode{SimpleFormatConverter} (protected inheritance, reusing its per-format conversion helpers without exposing \ccode{convert()}'s single-core meaning directly), splitting one conversion into a top half and a bottom half, one per core. Source: \lstinline[style=inlineFsRepo]!DualCoreFormatConverter.{h,cpp}!.

\begin{itemize}
 \item \ccode{setFrames(src, dst)}: computes the split point (\ccode{height / 2}, rounded down to an even row, so a \ccode{Mosaic8} source's 2$\times$2 \gterm{bayermosaic}{Bayer} pattern is never cut through the middle of a block) and configures both internal \ccode{HalfFrameWorker}s' source/destination pointers and dimensions accordingly.
 \item \ccode{convert(src, dst)} (override): \ccode{setFrames()} + \ccode{start()} + \ccode{awaitDone()} in sequence; throws \ccode{ExceptionFilter} with whichever worker's error if either failed. This is the method \repopath{main0.cpp}'s main loop actually calls; Paragraphs~\ref{subsec:fpgasteel-dualcore-forwarding-dispatch}--\ref{subsec:fpgasteel-dualcore-forwarding-cache-coherency} above are what happen underneath it.
 \item \ccode{start()} (override): dispatches the bottom-half worker to \term{CPU1}, then runs the top-half worker synchronously, in place, on \term{CPU0}.
 \item \ccode{awaitDone()} (override): busy-polls the bottom-half worker's status on \term{CPU1} until \ccode{Completed} or \ccode{Error}.
 \item \ccode{getWorker0()}/\ccode{getWorker1()} (override): accessors for the two \ccode{HalfFrameWorker}s.
 \item \ccode{isErrorOccured()}/\ccode{whatError(cpuNum)} (override): as \ccode{DualCoreJob} specifies.
 \item \ccode{HalfFrameWorker} (private nested class, extends \ccode{Worker} and protected \ccode{SimpleFormatConverter}): \ccode{run()} dispatches to the correct per-format helper for its half, then calls \ccode{alt_cache_l1_data_clean()} on the half it just wrote.
\end{itemize}

\section{How it works}
\label{sec:fpgasteel-dualcore-forwarding-how-it-works}

The following snippet is taken from \repopath{main0.cpp}:

\begin{lstlisting}[language=C++]
sys->init();
serial->init();
sys->prepareCacheSubsystem();
initCore();
// SCU + L2 + shared MMU table + CPU0's own
Core1 & core1 = Core1::getInstance();
core1.start();
// bring-up sequence, Section 10.4.1
while (core1.getStatus() != Core1::Status::Ready
 && core1.getStatus() != Core1::Status::Error) {}
if (core1.getStatus() == Core1::Status::Error) {
 serial->printf(" FAILED: %s\r\n", core1.whatError());
 while (true) {}
}
CacheAwareFramePool camPool(CAMERA_POOL_SIZE, FRAME_WIDTH, FRAME_HEIGHT,
 CAMERA_COLOR_SCHEME);
CacheAwareFramePool vgaPool(VGA_POOL_SIZE, FRAME_WIDTH, FRAME_HEIGHT,
 Frame::ColorScheme::RGB24);
vga->init(vgaPool);
pclkResetCtrl->deassertReset();
sys->delay(1000);
camera->init(camPool);
camera->verticalFlip(true);
camera->horizontalMirror(true);
hex->showDashes();
DualCoreFormatConverter converter;
while (true) {
 // ISR fault checks omitted here, see Camera::hasIsrFault()/Vga::hasIsrFault()
 if (camPool.available() > 0) {
  CacheAwareFrame * camFrame = camPool.pop(true);
  // invalidate: DMA wrote, CPU will read
  CacheAwareFrame * vgaFrame = static_cast<CacheAwareFrame *>(vgaPool.borrow());
  uint64_t t0 = sys->millis();
  converter.convert(*camFrame, *vgaFrame);
  // split across both cores, Sections 10.4.3-10.4.4
  uint64_t t1 = sys->millis();
  camPool.giveBack(camFrame);
  vgaPool.push(vgaFrame, true);
  // flush: CPU wrote, DMA will read
  hex->showNumber(static_cast<uint32_t>(t1 - t0));
 }
}
\end{lstlisting}

The only functional difference from Section~\ref{sec:fpgasteel-cache-forwarding-how-it-works} is \ccode{sys->prepareCacheSubsystem()} plus the \term{CPU1} bring-up-and-wait block before the pools are even constructed, and \ccode{DualCoreFormatConverter} standing in for Cache Forwarding Example's single-core conversion call; everything around it, descriptor ping-pong, ISR behavior, cache flush/invalidate placement, is identical.

\ccode{ExceptionFilter} joins the \gterm{exception}{exception} list this project's catch block handles, alongside every \gterm{exception}{exception} Cache Forwarding Example already lists (\ccode{ExceptionSystem}, \ccode{ExceptionSerial}, \ccode{ExceptionRingBuffer}, \ccode{ExceptionI2C}, \ccode{ExceptionCamera}, \ccode{ExceptionMsgdma}, \ccode{ExceptionHexDisplay}, \ccode{ExceptionFramePool}, \ccode{ExceptionFrame}).
